# Commercial V1 PR11B1 — Governed Examiner Execution + Trusted Atomic Initial-Grade Finalization

## Scope

PR11B1 starts from canonical base `0a4c5eb5db3f6a652064d2c3b25d1c2ed094b65a` on `commercial-v1-examiner-finalization` (the merged PR11A head, PR #11). Migrations 001-030 are byte-for-byte unchanged; the only migration this checkpoint adds is `202609160031_commercial_v1_examiner_grading.sql`.

This pass implements the first governed, provider-backed Examiner execution path and the trusted database finalizer that turns a validated provider grade into PR11A institutional result history — for the **first production grade only** (revision 1). No provider-backed execution, no AI grading and no trusted result writer existed before this checkpoint; 11A deliberately shipped none of them. Regrade/supersession, leaderboards and learner-facing grading UI remain out of scope.

**V2 correction pass (independent review):** the V1 patch's central atomic finalizer design was preserved; eight blockers were fixed in place, documented throughout this file and detailed in migration 031's own comments: (1) protected context now requires a fresh, dedicated `CONTEXT_READ` controller attestation, not merely ownership of a `RUNNING` execution UUID; (2) a same-target replay now checks for an existing Examiner execution claim _before_ the generic `ALREADY_GRADED` defence, preserving the original `resultRevisionId`; (3) an all-unanswered assessment (`marks:[]`) is now a valid `GRADED` response, and the unsupported `.max(200)` marks-count bound was removed; (4) real provider usage now survives every cleanup path — it is never coerced to zero once a provider call has actually consumed it; (5) terminal `FAILED`/`TIMEOUT`/`BUDGET_BLOCKED`/`CANCELLED` outcomes are now reported `UNAVAILABLE`, never the retryable-sounding `RETRY_LATER`, and `databaseTerminal` classification no longer treats `CONTEXT_CONFLICT` as a committed terminal state; (6) the exact reviewed `EXAMINER_COMMERCIAL_V1` runtime profile reference is now persisted, immutable, projected and bound into the HMAC canonical message; (7) the execution identity guard trigger now actually compares `component`/`practical_id`/`runtime_profile_ref` (previously claimed immutable in a comment but not enforced); (8) a TypeScript runtime test (`tests/commercial-v1-examiner-grading-runtime.test.ts`) now exercises the orchestration boundary with dependency-injected mocks.

**V3 correction pass (independent review):** three further blockers were found and fixed: (1) the production TypeScript command signer (`authority.ts`) never actually included `EXAMINER_RUNTIME_PROFILE_REF` in its AUTHORIZE/START/FINALIZE canonical message at all — meaning **no real production command MAC could ever verify** against migration 031's own `verify_command_ex1` (the V2 fix only reached the CONTEXT_READ signer). Now fixed, with a new, dedicated regression (`tests/commercial-v1-examiner-grading-authority.test.ts`) that exercises the real `attestExaminerExecutionCommand` implementation directly — never mocked — and independently recomputes the expected HMAC to prove the two sides agree; (2) AUTHORIZE's exact-target execution lookup now runs before the student's generic new-admission rate limits (previously a prior `SUCCEEDED` target could incorrectly surface as `RATE_LIMITED` merely because another target was active or the 5/60s-30/1h admission counters were exhausted), and the lookup is now explicitly actor-safe (filtered by `student_id=actor`, proven by a dedicated foreign-actor regression); (3) `mapExaminerAssessmentRuntimeResultToFinalizeCommand`/`mapExaminerLabRuntimeResultToFinalizeCommand` no longer coerce a malformed/out-of-envelope observed usage to a synthetic zero — they now return `null`, and the orchestrator makes no FINALIZE call at all in that case, falling back to the DB-owned 20-second expiry safety mechanism instead of ever risking a fabricated institutional usage record.

## Why a dedicated surface, not the generic role runtime

`ROLES_WITH_REVIEWED_EXECUTION_PATH` in `src/server/academic-runtime/index.ts` remains exactly `{"PROFESSOR"}`, textually unchanged. EXAMINER still resolves `NO_EXECUTION_PATH` through that generic boundary (proven by the pre-existing `tests/academic-runtime-composition.test.ts` suite, itself unmodified and still green). Grading is composed through a wholly separate module, `src/server/commercial-v1-examiner-grading/`, mirroring the architectural precedent of `src/server/tutor-lab-execution/` (docs/22) while diverging where the assessment firewall and result-finalization requirements are stronger:

- Tutor/Lab's governance surface centres on a 30-second **content release** scoped to a learner-chosen handoff, because its provider call answers a live conceptual question. Examiner has no such interactive lease: it grades one already-`SUBMITTED` attempt or one immutable lab submission, so migration 031 folds "open a scoped release" and "admit a provider execution" into a single MAC-gated AUTHORIZE step, and folds the entire trusted result write into the FINALIZE step of the very same governed command function (see "Atomic finalizer" below) — never a separate TypeScript-orchestrated multi-RPC sequence for the institutional write itself.
- Migration 031 reuses only the already-reviewed `academic_execution_private.controller_keys` HMAC trust root (migration 022) under a distinct protocol tag (`DUCELIO_COMMERCIAL_V1_EXAMINER_HMAC_SHA256_V1`) and policy version (`COMMERCIAL_V1_EXAMINER_V1`), so a Professor/Tutor/Lab attestation is structurally unable to authorize an Examiner transition and vice versa.

## New database objects

- `public.commercial_v1_examiner_executions` — the governed execution/claim record. A partial unique index on `attempt_id` (respectively `submission_id`) means **exactly one row is ever created per grading target**, full stop: a transient admission refusal (rate limit, target not yet eligible) writes no row at all and can be legitimately retried once the condition clears, but a real admitted claim (state `AUTHORIZED` or later) permanently occupies that target's one slot. This is simultaneously the database-backed concurrency claim (§12 of the brief) and the "initial grade only, no silent repeated provider grading" guarantee (§15) — no separate mechanism was needed for either. `commercial_v1_examiner_execution_usage` is the append-only, content-free usage ledger (identical shape to migrations 025/028's).
- `commercial_v1_examiner_private.verify_command_ex1` — HMAC verification for AUTHORIZE/START/FINALIZE, canonical message binding policy/role/**the fixed runtime profile ref**/key/actor/execution id/capability/target kind/attempt-or-submission id/enrolment-or-`NONE`/activation-or-`NONE`/operation/state/reason/budget stage/budget ceilings/usage/**grade digest**/issued+expiry.
- `commercial_v1_examiner_private.verify_context_read_ex1` — a SEPARATE, dedicated HMAC verification for the `CONTEXT_READ` operation (Blocker 1, below): a deliberately lighter parameter set (no state/reason/budget/usage/grade-digest exists for a read), same policy/protocol tag, distinct canonical operation value.
- `public.govern_commercial_v1_examiner_execution` — the one governed command surface (AUTHORIZE/START/FINALIZE), mirroring `govern_tutor_lab_provider_execution`'s shape. AUTHORIZE derives and validates the entire authoritative identity chain (ownership, `SUBMITTED` state, bound formal component or published lab policy, published result policy, absence of an existing production result) before ever creating the claim row.
- `public.get_commercial_v1_examiner_assessment_context` / `get_commercial_v1_examiner_lab_context` — the only readers of protected content (`expected_answer`, `marking_guidance`, submission/response bodies) for this checkpoint. See "Controller-attested context read" below.

## Controller-attested context read (Blocker 1)

The V1 patch gated protected context on ownership of a `RUNNING` execution UUID alone. **That was not sufficient**: an authenticated learner who happened to know (or could guess/enumerate) their own `RUNNING` execution id could call the context RPC directly, with no controller involvement at all.

Both context RPCs now additionally require a fresh, valid `CONTEXT_READ` attestation, verified independently by `commercial_v1_examiner_private.verify_context_read_ex1` — a MAC only the trusted server (holder of `ACADEMIC_EXECUTION_KEY_ID`/`ACADEMIC_EXECUTION_HMAC_KEY_HEX`) can produce, over a canonical message binding `COMMERCIAL_V1_EXAMINER_V1`, `EXAMINER`, the fixed runtime profile ref, key id, actor, execution id, capability, target kind, attempt-or-submission id, enrolment, activation, the literal operation `CONTEXT_READ`, and issued/expiry timestamps. Each RPC then re-checks the execution row is still owned by the caller, `RUNNING`, and **unexpired at read time** — an execution that has passed its `expires_at` is lazily transitioned to `TIMEOUT` in the same call (identical lifecycle semantics to the timeout handling inside `govern_commercial_v1_examiner_execution`) and the read fails closed with `EXECUTION_TIMEOUT`. Knowing a `RUNNING` execution UUID is therefore never, on its own, sufficient to read protected content.

`src/server/commercial-v1-examiner-grading/authority.ts`'s new `attestExaminerContextRead` produces this attestation server-side; `context.ts` calls it immediately before every context read and forwards only the signed bound parameters, never a raw MAC or key, to any other caller.

## Authoritative context construction (§6, §8)

`get_commercial_v1_examiner_assessment_context` re-derives, independent of any caller claim: the attempt, its assessment, its bound formal component, and returns, per **answered** question, position/prompt/real max marks/protected expected answer/protected marking guidance/the learner's own latest recorded response. An unanswered question is not merely marked "none" — it is **absent from the array entirely** (the underlying query's `join lateral ... on true` is an inner join against the response history; a question with no response row is excluded from the result set, not included with a null body). Only answered questions are ever sent to the provider — the trusted finalizer (not the model) supplies the deterministic zero for every unanswered authoritative question when it writes the result (see "Unanswered questions become zero" below; an assessment with zero answered questions legitimately yields `questions:[]`, see "All-unanswered assessments"). `get_commercial_v1_examiner_lab_context` re-derives the submission, its practical, the published lab policy's max marks/grading guidance, the submission body, and every objective the practical maps.

Neither function is ever reachable from a browser directly with useful effect: they are called only from `src/server/commercial-v1-examiner-grading/context.ts`, itself only imported by the server-only orchestrator, which forwards a bounded provider request — never this raw object — further.

## Provider output contract (§9)

`response.outputText` is parsed via `JSON.parse` — a markdown fence or any prose prefix/suffix already fails to parse before schema validation is reached. `examinerAssessmentProviderOutputSchema` / `examinerLabProviderOutputSchema` (`z.strictObject`, `src/domain/commercial-v1-examiner-grading.ts`) accept only `{"outcome":"GRADED","marks":[{"questionId","marksAwarded"}...]}` / `{"outcome":"GRADED","marksAwarded"}` or `{"outcome":"ESCALATE"}` — no rationale, feedback, answer-key echo or unknown key survives. `validateExaminerAssessmentMarks`/`validateExaminerLabMarks` then independently re-check the parsed marks against the SAME authoritative context sent to the provider (exact answered-question set, no duplicate/foreign id, no mark above the real max) — redundant with, never a substitute for, the database's own independent re-validation inside the atomic finalizer.

**All-unanswered assessments (Blocker 3):** the answered-question set may legitimately be empty (an attempt submitted with nothing answered). `marks:[]` is therefore a valid `GRADED` response, not a malformed one — the schema's earlier `.min(1)` was removed, along with an unsupported `.max(200)` upper bound (no immutable institutional assessment-question-count limit exists to justify one; the provider response text itself remains bounded by the existing, reviewed `outputText.max(20000)` in `src/server/academic-runtime/provider.ts`).

## Grade digest, not a trusted hash

The canonical message signs a **grade digest** (`sha256` hex of the normalized, order-independent marks text), never the raw marks. At FINALIZE, migration 031 independently **recomputes** this exact digest from the actual `p_assessment_marks`/`p_lab_marks_awarded` arguments and refuses any mismatch — a caller cannot substitute different marks under a stale signed digest, and the digest itself is bound by the MAC, so neither the marks nor the digest can be forged independently of the controller secret.

## Atomic finalizer — the critical success rule (§13)

`govern_commercial_v1_examiner_execution`'s FINALIZE branch, on `state='SUCCEEDED'`, is a single PL/pgSQL function invocation — one PostgreSQL transaction. Before any current-result observation or write it takes `select 1 from public.enrolments where id=... for update` — **the exact same enrolment row lock `attempt_commercial_v1_course_completion` (migration 030) already uses** — then, inside a nested `begin...exception when others...end` block (an implicit savepoint):

1. recomputes and verifies the grade digest;
2. validates the marks payload shape (assessment: unique ids, each a real question of this attempt's assessment, each answered, exactly the answered-question set — which may be empty; lab: bounded by the published policy max);
3. derives `component_weight_bp` (assessment) or `max_marks`/`contribution_bp` (lab) from the immutable PR10 grading policy / published lab policy — never from caller input;
4. inserts the revision-1 result header and question-mark rows (assessment) or the revision-1 lab result (lab) — these inserts hit PR11A's own `guard_assessment_result_insert` / `guard_assessment_question_mark_insert` / `guard_lab_result_insert` triggers (migration 030, unmodified), which independently re-validate the same identity chain a second time;
5. calls PR11A's own `commercial_v1_private.derive_and_insert_objective_outcomes` / `derive_and_insert_lab_objective_outcomes` — **reused, never duplicated**;
6. validates the complete revision with PR11A's own `commercial_v1_private.assessment_result_is_valid` / `lab_result_is_valid`;
7. only then updates the execution row itself to `SUCCEEDED` with the result's id and the grade digest.

If any step raises, the exception handler catches it, the savepoint rolls back every result-side write, and the execution row is instead durably recorded `FAILED`/`RESULT_INTEGRITY_FAILED` in the same transaction. **A result can never exist while its Examiner execution remains non-successful, and an execution can never be `SUCCEEDED` while its result is missing or invalid** — both are the same atomic write, not two coordinated ones.

Remediation reconciliation needs no extra call here: PR11A's existing `AFTER INSERT` triggers on the objective-outcome tables (migration 030) already fire from step 5 above, using the exact same mechanism 11A's own tests exercise. `ESCALATE` and every other non-`SUCCEEDED` terminal state write no result row at all.

## Unanswered questions become zero (§7)

The finalizer's per-question insert loop iterates every real `assessment_questions` row for the attempt's assessment (not only the ones the provider graded), taking each one's mark from the provider payload when present or `0` otherwise. The stored result therefore always has exactly one question-mark row per real question, with unanswered ones set to the deterministic zero the database itself supplies — the model never assigns it. When every question is unanswered, the same loop still produces one zero-valued row per question from an empty `marks:[]` payload.

## Duplicate provider calls prevented (§12)

Because the unique-index claim above admits **at most one** `AUTHORIZED`-or-later row per target ever, and AUTHORIZE for an already-occupied target either loses the race (`REPLAY_REJECTED` while non-terminal) or is handed back that row's own terminal snapshot (idempotent replay after `SUCCEEDED`/`FAILED`/`ESCALATED`/`TIMEOUT`, `transitioned:false`), a second concurrent or replayed request can never reach a second provider call for the same target. AUTHORIZE additionally enforces a per-student "one `AUTHORIZED`/`RUNNING` execution at a time" ceiling plus 5/60s and 30/1h admission ceilings, mirroring migrations 025/028 exactly — but only once the exact-target lookup below has already found nothing to say about the target (see Blocker 2).

There is deliberately **no automatic retry after a terminal outcome** — including transient-looking ones like a provider timeout. Regrade/retry policy is explicitly future work (§15 of the brief); this checkpoint does not invent one.

## Successful replay preserves the original result (Blocker 2)

AUTHORIZE checks for an existing Examiner execution claim for the EXACT target **first** — before the student's generic new-admission rate limits, the budget-envelope check, fresh-target eligibility checks, and the generic "a production result already exists" defence. Without this ordering, a prior `SUCCEEDED` target could incorrectly surface as `RATE_LIMITED` merely because another target happened to be active, or because the student's 5/60s or 30/1h admission counters were exhausted for unrelated reasons — neither of which has anything to do with a target that was already resolved. If this checkpoint's own execution history already has a (possibly terminal) claim for the target, AUTHORIZE returns that claim's own current projection — `transitioned:false`, and for a prior `SUCCEEDED` grade, the exact original `resultRevisionId`, execution id and state — rather than a bare `ALREADY_GRADED` or admission-limit denial that would both discard it. `ALREADY_GRADED` remains reachable, but only when no Examiner execution has ever claimed the target and a production result nonetheless exists (historical/external result state, e.g. a hypothetical future manual/service-authored result) — a defence-in-depth path with no execution row to prefer, since `guard_assessment_result_insert`/`guard_lab_result_insert` (migration 030) would refuse a second revision-1 write for that target anyway.

The lookup is explicitly **actor-safe**: it is filtered to `student_id=actor`, so a caller probing with a foreign attempt/submission id observes nothing here and falls through to the ordinary ownership check, which returns the same bounded `NOT_FOUND_OR_FORBIDDEN` it always has — never another student's execution projection, state or `resultRevisionId`.

## Runtime profile persistence (Blocker 6)

`commercial_v1_examiner_executions.runtime_profile_ref` is a new `not null default 'EXAMINER_COMMERCIAL_V1' check(runtime_profile_ref='EXAMINER_COMMERCIAL_V1')` column: the exact reviewed, code-owned runtime/model profile this execution was admitted under, immutable once inserted (protected by the identity guard trigger, below), exposed in `execution_projection` as `runtimeProfileRef`, included in the content-minimised audit row, and part of the domain `examinerExecutionSnapshotSchema`. It is also bound into both HMAC canonical messages as a fixed literal (`'EXAMINER_COMMERCIAL_V1'`) rather than a caller-supplied parameter — a future checkpoint that changes the profile ref must also change that literal, itself a reviewed migration diff, so execution policy/profile provenance cannot drift silently. Never accepted from the learner/browser.

## Execution identity immutability (Blocker 7)

The guard trigger's identity-tuple comparison now actually includes `component`, `practical_id` and `runtime_profile_ref` (previously claimed immutable in a comment but not compared, so an `UPDATE` could have silently changed them). Every institutional identity/policy/budget binding derived at AUTHORIZE — student, capability, target kind, attempt/submission, component/practical, policy version, execution kind, runtime profile ref, creation/authorization timestamps, admitted budget ceilings — is immutable for the row's remaining life; only `result_revision_id`/`state`/`reason_code`/`budget_stage`/`started_at`/`terminal_at`/`grade_digest`/`review_path` may ever change, and only along the already-reviewed legitimate transitions.

## Terminal-status mapping (Blocker 5)

`src/server/commercial-v1-examiner-grading/index.ts`'s `mapSnapshotToResult` now maps every terminal `FAILED`/`BUDGET_BLOCKED`/`TIMEOUT`/`CANCELLED` snapshot to the caller-facing `UNAVAILABLE` status — never `RETRY_LATER`, since 11B1 deliberately has no regrade/retry authority and reporting a permanently terminal outcome as retryable would be dishonest. `RETRY_LATER` is reserved for genuinely transient, pre-terminal denials only: `RATE_LIMITED` (including the "one active claim per student" ceiling) and `REPLAY_REJECTED` (a lost race against a concurrent AUTHORIZE for the same target, while that other claim is still non-terminal). `OUT_OF_ENVELOPE` — a configuration/policy failure, not a transient condition — now maps to `UNAVAILABLE`.

`src/server/commercial-v1-examiner-grading/authority.ts`'s `databaseTerminal` classification was also corrected: it is `true` only for `EXECUTION_TIMEOUT`, the one denial that genuinely commits a terminal state transition as a side effect of the denial itself (migration 031's lazy-timeout branch). `CONTEXT_CONFLICT` — a pure read-time refusal that mutates nothing — is no longer treated as database-terminal, so a legitimate best-effort `FAILED` cleanup attempt is no longer wrongly skipped after it.

## Real provider usage survives cleanup (Blocker 4)

`gradeExaminerTarget` now tracks the latest real `RuntimeResult` once a provider call has actually happened (`providerResult`, read via `lastKnownUsage()`). Every cleanup/best-effort `FINALIZE(FAILED, INTERNAL_ERROR)` call — including the one issued after a post-provider `FINALIZE(SUCCEEDED)` transport/controller failure — now carries that real, possibly non-zero `providerCalls`/`attempts`/token/cost/`elapsedMs` usage, never a silently coerced `zeroUsage()`. Zero usage remains correct, and is still used, for the genuinely zero-usage case: a failure before any provider call was ever attempted (e.g. context construction throwing).

## Never coerce known usage to zero (Blocker 3, V3)

`mapExaminerAssessmentRuntimeResultToFinalizeCommand`/`mapExaminerLabRuntimeResultToFinalizeCommand` previously fell back to a synthetic all-zero `ExaminerUsageReport` whenever `result.usage` failed `examinerUsageReportSchema`. Given the current reviewed HTTP_JSON provider bounds, real legitimate usage always fits that schema — a failure here represents an internal invariant violation, never a legitimate reason to invent zero institutional accounting. Both functions now return `null` in that case (via a shared `parseKnownUsage` helper), and the orchestrator (`src/server/commercial-v1-examiner-grading/index.ts`) makes **no FINALIZE call at all** when it receives `null` — it returns `UNAVAILABLE` and leaves the execution to the existing DB-owned 20-second expiry safety mechanism rather than risk fabricating a usage record. This does not change the Blocker 4 cleanup path: `lastKnownUsage()` still forwards `providerResult.usage` directly for the post-provider-transport-failure cleanup case, since that usage was already legitimately observed and must not be lost either.

## Runtime profile

`EXAMINER_COMMERCIAL_V1` (`src/server/academic-runtime/profile-registry.ts`), added additively alongside the existing Professor/Tutor/Lab entries: `HTTP_JSON` adapter, `maxProviderCalls:1`, `maxAttempts:1`, `maxInputContextBytes:128000`, `maxOutputTokens:1200`, `totalDeadlineMs:15000`, `maxEstimatedCostMicrousd:50000` — comfortably inside migration 031's own DB ceiling (`max_output_tokens between 1 and 1200`, `max_estimated_cost_microusd between 1 and 50000`, `max_provider_calls=1`). No vendor SDK, no course-configurable override: `src/server/commercial-v1-examiner-grading/index.ts` always resolves this exact ref directly, never through a stored `academic_agent_configs.modelProfileRef` lookup — there is no per-course "enable Examiner" toggle in 11B1 (see Known limitations).

## Entrypoints

`gradeControlledAssessmentAttempt({attemptId})` / `gradePracticalLabSubmission({submissionId})` (`src/server/commercial-v1-examiner-grading/index.ts`) — identifier-only input (`z.strictObject`, no `marks`/`score`/`weight`/`expectedAnswer` field is ever accepted), learner-self-scoped (`requireStudentPrincipal`). Every other identifier (enrolment, activation, component/practical, weight, max marks, contribution) is derived and re-validated entirely server-side.

## Security

No new result table gains direct learner/authenticated mutation access — reads and writes to `commercial_v1_examiner_executions`/`commercial_v1_examiner_execution_usage` happen only through the governed RPCs, closed by the same effective-ACL do-block acceptance pattern as migrations 022/025/028/030. `service_role`/`anon` cannot invoke the governed RPC or read the tables directly. Audit rows (`commercial_v1_examiner_private.audit_execution`) carry only identifiers/state/usage/the grade digest/the runtime profile ref — never raw provider output, an answer key, a learner response body or a submission body.

## Known limitations (deliberately not implemented / not proven)

- **PGlite cannot prove true multi-connection PostgreSQL concurrency.** The one-claim-per-target guarantee rests on a real PostgreSQL unique-index constraint and an `insert ... on conflict do nothing` race-safe by Postgres's own construction, but this repository's test harness is single-connection; no test here opens two genuinely concurrent database connections to race two AUTHORIZE calls against each other. This is the same limitation already documented for migrations 025/026/027/028's own concurrency posture — not a new gap this checkpoint introduces, but not newly resolved either.
- **Superseded by PR16A (migration 036).** Normal learner-initiated INITIAL Examiner grading now IS programme-version config governed: the database's own AUTHORIZE reads the current EXAMINER `academic_agent_configs` row (under the same `programme_versions` lock `set_agent_config` uses) before admitting a claim, denies `POLICY_BLOCKED` when no row exists, the row is disabled, or the invoked capability (`grade_controlled_assessment`/`grade_practical_lab`) is not requested, denies `UNKNOWN_MODEL_PROFILE` for an invalid/cross-role stored profile ref, and creates a durable direct `ESCALATED` claim when `escalationPolicy=ACADEMIC_REVIEW`. An institution can now disable AI-assisted grading per course through the existing agent-configuration surface. See PR16A's checkpoint documentation (`docs/implementation-progress.md`) for the corrected design; the administrative regrade plane (migration 032) remains fixed-profile and untouched.
- **A terminal `FAILED`/`TIMEOUT`/`ESCALATED`/`BUDGET_BLOCKED`/`CANCELLED` outcome permanently occupies its target's one-claim slot in 11B1.** Because no regrade/retry authority exists yet (deliberately, per the brief), a transient provider failure or timeout means that exact attempt/submission can never be graded through this Examiner path again without a future, separately reviewed regrade checkpoint.

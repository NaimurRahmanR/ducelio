# Commercial V1 — Governed Tutor + Lab Instructor Execution

## Starting state and scope

Started from clean `commercial-v1-tutor-lab-execution` at `b4cf76354210d7b653010ddc8a61491aca75d139`, the PR #8 Course Activation & Cohort Delivery Materialisation merge. The local baseline was 978 tests across 48 files on bundled Node. Independent implementation review is complete. The implementation was merged via PR #9 at main `176205c4e4009ec5b87dfed60a1412f12bee1f2a`; both PR-head CI and post-merge main CI passed.

This checkpoint turns the existing deterministic Tutor/Lab Instructor handoff architecture (`src/domain/delivery.ts`, migration 023) into real, governed, provider-backed learner support — reusing the provider-neutral runtime harness Professor already established, but through a **structurally separate governance surface**. It does not add TUTOR/LAB_INSTRUCTOR to `ROLES_WITH_REVIEWED_EXECUTION_PATH` (that set remains exactly `{"PROFESSOR"}`, unchanged) and does not touch migrations 021/025 (Professor's content-release and provider-execution tables remain hard-coded to `agent_profile='PROFESSOR'`, untouched). Examiner and Counsellor remain non-executing. No grading, no institutional-state mutation, no hosted provider call was made here.

**Correction pass (independent review):** the initial implementation passed its own local gates but an independent review of the actual patch found five confirmed blockers plus a security-test acceptance gap, all fixed in place (migration 028 was still uncommitted at that review stage, so it was corrected rather than superseded): (1) a replayed `request_practical_support` call could keep an already-linked practical while reporting success for a _different_ same-kind practical in the same lesson — fixed by verifying the actual stored link after insert and failing `CONTEXT_CONFLICT` on any mismatch; (2) provider context received the destination role (`"TUTOR"`/`"LAB_INSTRUCTOR"`) as its reason code instead of the real handoff reason — fixed by returning the authoritative `reason_code` from `begin_tutor_lab_content_release` and threading it through as `release.reasonCode`; (3) a stored agent configuration could name any resolvable profile ref, including Professor's or the other role's — fixed with an explicit code-owned role→profile binding checked before AUTHORIZE; (4) Tutor/Lab objective context silently truncated to the first 50 lesson objectives, so a requested or mapped objective beyond that page could resolve to `null` or a partial set — fixed with bounded, capped pagination that either resolves exactly or fails `CONTEXT_CONFLICT`; (5) the idempotency reservation RPC inserted before proving the caller owned the referenced handoff — fixed by re-deriving ownership first, identically to `begin_tutor_lab_content_release`. The security-test acceptance gap (direct time-of-check/time-of-use assessment-firewall tests across the release/AUTHORIZE/context/close boundaries) is now covered directly. A non-blocking truth-sync also corrected `maxAttempts` from 2 to 1 for both new profiles, since the shared runtime harness could never actually reach a second provider call with `maxProviderCalls` fixed at 1. Each fix and its regression tests are detailed in the relevant section below.

**Final correction pass (independent re-review):** re-review of the corrected patch confirmed the five blockers above were fixed, and found one further execution-authority blocker plus three truth-sync corrections, all fixed in place: (6) `executeTutorLabSupport` read agent configuration a second time, later than the context builders' own read, but never re-checked THAT later configuration's capabilities against the context it had already built — an admin narrowing a capability (while leaving the role enabled and its profile ref unchanged) between those two reads could otherwise let a provider call proceed on content the current configuration no longer authorizes. Fixed by re-validating, against the exact same code-owned capability catalogue, that the final configuration still authorizes `get_lesson_context`/`get_lesson_objectives` (both roles) and `get_learning_resources` (Tutor only, and only when the already-built context actually included resources) — before AUTHORIZE and before any provider call. Two documentation claims were also corrected for accuracy rather than behaviour: the assessment-firewall section previously implied an `ACTIVITY_BLOCKED` denial writes zero release rows, when migration 028 in fact deliberately persists one terminal `BLOCKED` release receipt as immutable denial/audit provenance (a new DB regression test now proves this receipt exists, is inert, and authorizes zero provider executions); and migration 028's own comment describing retry semantics was corrected to say plainly that a second provider attempt is unreachable once `max_provider_calls=1`, regardless of a runtime profile's `maxAttempts`. A stale test-fixture mock (`maxAttempts: 2` in the Tutor/Lab runtime test's default mock, left over from before the earlier truth-sync) was also corrected to `1`. See the relevant sections below for detail.

## Migration 028 and why a separate surface, not a Professor extension

`202609140028_commercial_v1_tutor_lab_execution.sql` is additive; migrations 001–027 are byte-for-byte unchanged (verified: zero diff). It introduces `TUTOR_LAB_EXECUTION_V1`/`PROVIDER_BACKED_V1`, a governance surface generalised across exactly `TUTOR` and `LAB_INSTRUCTOR` — one coherent migration, not two per-role migrations, since the two roles share an identical lifecycle shape and only differ in which context each builds.

Professor's `academic_content_releases` (migration 021) hard-codes `agent_profile text not null default 'PROFESSOR' check(agent_profile = 'PROFESSOR')`, and `academic_provider_executions` (migration 025) does the same. Widening either CHECK constraint would silently redefine what a historical Professor row means and requires editing an immutable migration — explicitly excluded. Instead, migration 028 adds its own parallel tables with the identical lifecycle shape (30-second release window; `AUTHORIZED → RUNNING → {SUCCEEDED,FAILED,ABSTAINED,ESCALATED,BUDGET_BLOCKED,TIMEOUT,CANCELLED,BLOCKED}` execution states; the same immutability/audit trigger pattern) but constrained to `agent_profile in ('TUTOR','LAB_INSTRUCTOR')`, and reuses only the already-reviewed `academic_execution_private.controller_keys` HMAC trust root (migration 022) under a distinct protocol tag (`DUCELIO_EXECUTION_HMAC_TUTOR_LAB_V1`) and policy version (`TUTOR_LAB_EXECUTION_V1`), so a Professor V2 attestation is structurally unable to authorize a Tutor/Lab transition and vice versa — proven directly: `govern_professor_provider_execution` cannot see a `tutor_lab_content_releases` row at all (it queries `academic_content_releases`), and a Tutor/Lab-signed MAC fails `verify_command_v2`'s own bounds/tag check.

## New database objects

- `public.tutor_lab_handoff_practicals` — additive provenance: links a `PRACTICAL_HELP`/`PRACTICAL_PREREQUISITE` handoff to the exact `course_practicals` row that generated it, since `delivery_handoffs` (migration 023, untouched) has no `practical_id` column and a lesson can have more than one practical. Populated only by a `CREATE OR REPLACE FUNCTION public.request_practical_support(...)` (same signature migration 027 defined; migration 027's file is untouched, only the live function body is extended) at the moment the handoff is created — never inferred later, never from title/order. **Correction pass (Blocker 1):** `request_delivery_handoff`'s own idempotency identity (`requested_by, request_id`, migration 023) cannot know about `practical_id` at all, so two different same-kind practicals in one lesson could legitimately share a replayed `request_id`. `request_practical_support` now re-reads the actual stored link after its atomic insert-or-noop and raises `CONTEXT_CONFLICT` if it doesn't match the caller's own `p_practical_id` — race-safe under the table's primary key, since every racer's post-insert read sees the same single admitted value.
- `public.get_owned_practical(enrolment_id, practical_id)` — re-derives ownership from the caller's own enrolment (reusing migration 027's `course_activation_private.student_enrolment`) and the same activated-cohort join `list_my_practicals` already uses; the only way Lab context ever reads practical content.
- `public.tutor_lab_content_releases` — the generalised release, bound to `student_id, invocation_id, agent_profile (TUTOR|LAB_INSTRUCTOR), enrolment_id, handoff_id, lesson_id, objective_id, practical_id`. A CHECK constraint (`(agent_profile='LAB_INSTRUCTOR') = (practical_id is not null)`) makes the role/practical binding structurally exact: Lab always has a practical, Tutor never does.
- `public.begin_tutor_lab_content_release(invocation_id, handoff_id)` / `close_tutor_lab_content_release(release_id, complete)` — the sole way a release opens/closes. **The caller supplies no role at all** — the destination role is read exclusively from `delivery_handoffs.destination_profile`, eliminating "forged role" as a possibility by construction, not merely by a later check.
- `public.tutor_lab_provider_executions` / `tutor_lab_provider_execution_usage` — the generalised, content-free execution/usage ledger, identical shape to migration 025's, with its own (tighter) DB-owned ceiling.
- `tutor_lab_execution_private.verify_command_tl1` / `public.govern_tutor_lab_provider_execution` — the MAC-attested AUTHORIZE/START/FINALIZE command surface, role-parameterised, mirroring `govern_professor_provider_execution` exactly.
- `public.tutor_lab_interaction_reservations` — idempotency, `primary key(student_id, idempotency_key)`, mirroring migration 026's `professor_classroom_interaction_reservations` pattern.

All new tables are RLS-enabled with `public`/`anon`/`authenticated`/`service_role` explicitly revoked at table, column, schema and function level, closed by an effective-ACL assertion that fails migration deployment on any unsafe inherited privilege (mirroring migrations 022/024–027 exactly).

## Tutor execution contract

Reviewed handoff reasons `MISSED_LESSON_PRACTICE`, `OBJECTIVE_REINFORCEMENT`, `PRACTICAL_PREREQUISITE` route to `TUTOR` (this mapping is fixed at handoff-creation time in migration 023, untouched, and re-verified by `begin_tutor_lab_content_release` reading `destination_profile`). `OBJECTIVE_REINFORCEMENT` requires the handoff's own `objective_id` to be present — a handoff missing it fails closed with `INVALID_INPUT` at release-open time, never reaching a provider call. `PRACTICAL_HELP` routed to Tutor, or any other reason code, is rejected with `CONTEXT_CONFLICT`.

## Lab Instructor execution contract

Only `PRACTICAL_HELP` routes to `LAB_INSTRUCTOR`. The exact practical is resolved via `tutor_lab_handoff_practicals` (never from caller input, never from title/package JSON) and re-verified as belonging to the caller's own activated cohort/programme version. Any other reason code routed to Lab fails with `CONTEXT_CONFLICT`; an unlinked or foreign practical fails with `NOT_FOUND_OR_FORBIDDEN`.

**Correction pass (Blocker 2, authoritative reason code):** `begin_tutor_lab_content_release` now returns the handoff's own `reason_code` in its grant JSON, parsed into `TutorLabContentRelease.reasonCode` (`src/server/tutor-lab-execution/release.ts`, re-validated there against `TUTOR_LAB_ALLOWED_REASONS[role]` as a second, defense-in-depth check). `buildTutorContext`/`buildLabContext` (`src/server/tutor-lab-execution/context.ts`) now take only the `release` and read `release.reasonCode` directly — never the role name, and never a value the caller could supply, since `TutorLabSupportRequest` has no `reasonCode` field at all. Provider context therefore always carries one of `MISSED_LESSON_PRACTICE`/`OBJECTIVE_REINFORCEMENT`/`PRACTICAL_PREREQUISITE`/`PRACTICAL_HELP`, never the string `"TUTOR"` or `"LAB_INSTRUCTOR"`.

## Request shape

```ts
{ handoffId: UUID, message: string /* trimmed, 1..2000 */, idempotencyKey: UUID }
```

`tutorLabSupportRequestSchema` (`src/domain/tutor-lab-execution.ts`) is a `z.strictObject` — no `role`, `provider`, `model`, `capability`, `budget` or `reasonCode` field is ever accepted; a form supplying extra fields has them silently ignored by the Server Action's own explicit `FormData` field reads (`src/app/student/practicals/actions.ts`), never passed through. The destination role, enrolment, lesson, objective, practical **and reason code** are all derived server-side from the handoff alone.

## Provider profiles and budgets

Two new, separately reviewed Commercial V1 profiles in the existing code-owned registry (`src/server/academic-runtime/profile-registry.ts`), deliberately **not** a semantic reuse of `PROFESSOR_COMMERCIAL_V1`:

| Field                      | `TUTOR_COMMERCIAL_V1` | `LAB_INSTRUCTOR_COMMERCIAL_V1` |
| -------------------------- | --------------------- | ------------------------------ |
| `adapterKind`              | `HTTP_JSON`           | `HTTP_JSON`                    |
| `maxProviderCalls`         | 1                     | 1                              |
| `maxAttempts`              | 1                     | 1                              |
| `maxInputContextBytes`     | 12,000                | 12,000                         |
| `maxOutputTokens`          | 700                   | 700                            |
| `totalDeadlineMs`          | 15,000                | 15,000                         |
| `maxEstimatedCostMicrousd` | 30,000                | 30,000                         |

The DB-owned hard ceiling (`TUTOR_LAB_EXECUTION_DB_CEILING`, migration 028's table CHECK constraints) fixes `max_provider_calls` at **exactly 1** (no demonstrated need for more), `max_output_tokens` at 1..2000 and `max_estimated_cost_microusd` at 1..100,000 — tighter than Professor's 1..3/1..4000/1..200,000, appropriate for bounded learner-support guidance rather than a full lesson explanation. A proposal above this ceiling is rejected at the cryptographic layer (`UNTRUSTED_EXECUTION`) before AUTHORIZE's own business logic is ever reached; a degenerate in-bounds-but-zero proposal is refused by AUTHORIZE itself (`BLOCKED`/`OUT_OF_ENVELOPE`). No credential or endpoint is added; `resolveAdapterForProfile` still fails closed to `NO_PROVIDER_CONFIGURED` without `ACADEMIC_PROVIDER_BASE_URL`/`ACADEMIC_PROVIDER_API_KEY`.

**Final correction pass (migration comment truth-sync):** migration 028's own comment on `tutor_lab_provider_executions` previously implied bounded retry/attempt semantics live in the runtime profile's `maxAttempts`, independent of this DB ceiling. That was misleading: the shared runtime harness (`src/server/academic-runtime/runtime.ts`) checks `providerCalls >= maxProviderCalls` before every attempt, so once this DB ceiling admits `max_provider_calls=1`, a second provider attempt is structurally unreachable regardless of what `maxAttempts` says — which is exactly why both profiles above now declare `maxAttempts: 1`, truthfully expressing "exactly one provider attempt/call," never a retry. The comment is corrected to say this plainly.

## Content-release and execution lifecycle (critical success rule)

Identical guarantee to Professor's (`docs/19-live-professor-execution.md`): **no `SUCCEEDED` response ever escapes before the content release has closed successfully AND the FINALIZE call is itself confirmed by the database.** Concretely, `src/server/tutor-lab-execution/index.ts`'s `executeTutorLabSupport`:

1. Reserves the idempotency key (`reserve_tutor_lab_interaction`) — before anything else, so two simultaneous duplicate actions can never both reach a release.
2. Opens the release (`begin_tutor_lab_content_release`) — derives role/ownership/reason validity here; a denial that occurs before the row is inserted (`UNAUTHENTICATED`/`FORBIDDEN`/`NOT_FOUND_OR_FORBIDDEN`/`NO_EXECUTION_PATH`/`CONTEXT_CONFLICT`/`INVALID_INPUT`) returns immediately with no release row at all. An `ACTIVITY_BLOCKED` denial is different: the row is already inserted (terminal `BLOCKED` state) before the firewall check runs, so this specific denial returns immediately with one persisted, inert receipt rather than zero rows — see "Assessment firewall" below.
3. Builds the role-specific context (`buildTutorContext`/`buildLabContext`), which independently re-checks the assessment firewall and the role's own capability allowlist a second time.
4. Re-reads agent configuration and re-validates, against this final read, every capability that materially contributed to the context just built (`get_lesson_context`/`get_lesson_objectives` always, `get_learning_resources` only when Tutor's context actually included resources) — closing the gap between the context builders' own (earlier) capability read and this later one.
5. AUTHORIZE → START → run the provider (`runGovernedProviderExecution`, the exact same provider-neutral harness Professor uses) — captured, never returned yet.
6. Closes the release with `complete = (context built successfully)`. A close failure discards any provider success and best-effort FINALIZEs the execution `FAILED`/`CONTENT_RELEASE_UNAVAILABLE`.
7. Only once the release closed successfully does FINALIZE run, mapping the real `RuntimeResult` onto the bounded vocabulary; a state mismatch or FINALIZE failure returns `RETRY_LATER`, never a fabricated success.

This is sequential TypeScript orchestration over separate RPC calls (not a single nested-callback gateway like Professor's `withValidatedProfessorContent`), because Tutor/Lab context has no capability-selection axis to negotiate — it is entirely determined by the handoff. The same ordering guarantee holds regardless of the different call shape.

## Handoff and practical ownership — how forgery fails closed

`begin_tutor_lab_content_release` proves, in one transaction: `current_app_user() = delivery_handoffs.requested_by` AND `enrolments.student_id = current_app_user()` for the handoff's own `enrolment_id` — a forged, foreign, or nonexistent `handoffId` returns `NOT_FOUND_OR_FORBIDDEN` before any other check runs. `get_owned_practical` independently re-derives the exact same ownership a second time (defense in depth) via the caller's own enrolment and the activated-cohort join. Multi-role staff accounts (e.g. an account holding both STUDENT and ACADEMIC_ADMIN) gain no broader visibility: ownership is checked by exact `student_id`/`requested_by` equality, never by role.

**Correction pass (Blocker 5):** `reserve_tutor_lab_interaction` now proves this exact same ownership (`requested_by`/`student_id` equality) **before** its insert, not only at the later release-open step — a foreign learner's real handoff and a wholly nonexistent handoff both return the identical bounded `NOT_FOUND_OR_FORBIDDEN` result, with zero reservation row created either way, so a learner can never create immutable reservation provenance against a handoff they don't own, and cannot distinguish "exists but foreign" from "doesn't exist" by observing the outcome.

## Idempotency and concurrency

`public.tutor_lab_interaction_reservations`, `primary key(student_id, idempotency_key)`, written via one atomic `insert ... on conflict do nothing` (mirroring migration 026's professor-classroom pattern) — never a "compare against the latest key" design. A fingerprint (`sha256(handoffId + "\n" + message)`) is stored alongside the key: a replay with the identical fingerprint is a safe `DUPLICATE` (no second provider call, no content re-sent — transcripts are never persisted, so a duplicate reports only that status, never replayed text); a replay with the SAME key but a DIFFERENT handoff or message fails closed as `DUPLICATE_KEY_CONFLICT`, never silently proceeding under a stale reservation. Reservation happens **before** the release ever opens, and now also before ownership of the handoff is even assumed (see above), so two simultaneous identical requests can never both reach the provider. The insert's own unique-index conflict resolution is atomic by PostgreSQL construction; this repository's PGlite test harness is single-connection and cannot itself exercise true concurrent load, so hosted concurrent-connection acceptance remains a separate, outstanding item — exactly as already documented for migrations 025/026/027's own concurrency posture.

**AC-4 amendment ([docs/46](46-agent-behaviour-ac4.md)):** the fingerprint now also covers the learner's choice to keep a Tutor class note. An omitted or false choice keeps exactly the material above, `handoffId + "\n" + message`, so historical reservations still replay. `saveAsClassNote = true` appends the domain separator `"\nAC4_SAVE_AS_CLASS_NOTE"`, so the same key with a different note choice is a `DUPLICATE_KEY_CONFLICT`. Migration 028 and its reservation table are unchanged.

## Assessment firewall

Enforced independently at multiple layers, so a stale/replayed handoff created before a controlled assessment started is still blocked: `begin_tutor_lab_content_release` checks `academic_content_release_explain_allowed()` (the same function gating Professor's release and `get_delivery_agent_access`) as part of the same insert that creates the release row, so a blocked attempt returns `ACTIVITY_BLOCKED` with **no ACTIVE/releasable content-release authority ever granted** — but the row itself is not skipped: one terminal `BLOCKED` release receipt is persisted (state `BLOCKED`, `terminal_at` set immediately, `expires_at` remains 30 seconds after `started_at` while `terminal_at` is set immediately), the same immutable denial/audit provenance pattern used elsewhere in this schema, and it is fail-closed by construction — a `BLOCKED` release can never later be completed (`close_tutor_lab_content_release` on it is a no-op, `transitioned: false`) and it authorizes zero provider executions (proven directly: `tutor_lab_provider_executions` has zero rows referencing it). **Documentation truth-sync (final correction pass):** an earlier revision of this document incorrectly said this denial writes "zero release rows" — corrected here; the distinction that matters is a terminal `BLOCKED` receipt (persisted, inert, non-authorizing) versus `ACTIVE` content-release authority (never granted), not row count. The context builders (`getStudentLessonContext`/`getStudentLessonObjectives`/`getStudentLessonResources`/`get_owned_practical`) independently re-check the same firewall a second time. AUTHORIZE, START and close-release each re-check it a third, fourth and fifth time. Tested directly: starting a real controlled-assessment attempt, then attempting to open a release against a handoff created _before_ that attempt started, is blocked with zero provider calls for both Tutor and Lab, and (new regression) the persisted `BLOCKED` receipt itself is proven to exist, be inert, and authorize zero executions.

**Correction pass (security-test acceptance gap):** four additional time-of-check/time-of-use scenarios are now tested directly, each starting a release/execution while `NORMAL` and only then starting a real controlled-assessment attempt: (A) a release already open, assessment starts, then AUTHORIZE — denied `ACTIVITY_BLOCKED`, zero executions ever created for that release; (B) AUTHORIZE already succeeded, assessment starts, then START — denied `ACTIVITY_BLOCKED` and the execution is durably terminalized `FAILED`, never left dangling `AUTHORIZED`; (C) a context read (`get_owned_practical`, the exact RPC Lab context construction calls) against an already-open release, once the firewall is active — fails closed; (D) AUTHORIZE and START both already succeeded (provider output would be held only in the caller's own process memory at this point, never persisted mid-flight), assessment starts, then `close_tutor_lab_content_release(id, true)` — the release reports `ABORTED`, never `COMPLETED`, which is exactly the signal `closeTutorLabContentRelease` (TypeScript) treats as a throw, causing the real composition boundary (`executeTutorLabSupport`) to discard any captured provider success and FINALIZE the execution as a genuine `FAILED` instead (see the existing "a release-close failure discards a genuine provider success" runtime test for that half of the guarantee).

## Practical materialisation reuse

Lab Instructor reads `course_practicals`/`course_practical_objectives` (migration 027) exclusively through `get_owned_practical`; it never reads `course_package_imports.raw_package` at learner runtime. Practical identity is resolved via the `tutor_lab_handoff_practicals` link recorded at handoff-creation time, never by title, order or caller-supplied practical ID alone in isolation.

## Capability enforcement

Tutor/Lab context builders (`src/server/tutor-lab-execution/context.ts`) call `getAgentConfigForEnrolment` and `isCapabilityAuthorized` — the exact same code-owned catalogue (`src/domain/academic-capability-policy.ts`) already reviewed for these roles: `TUTOR` = `{get_current_learner_context, get_lesson_context, get_lesson_objectives, get_learning_resources}`, `LAB_INSTRUCTOR` = `{get_current_learner_context, get_lesson_context, get_lesson_objectives}` — **no `get_learning_resources` for Lab**, unchanged; this checkpoint does not widen either catalogue. `get_lesson_context`/`get_lesson_objectives` are required (a disabled config or a missing capability fails closed to a safe `UNAVAILABLE` before any provider call); `get_learning_resources` is optional for Tutor — its absence simply omits resources from context rather than failing the whole request. Stored configuration can only narrow, never widen, what the code-owned catalogue already allows.

**Final correction pass (execution-authority blocker):** the capability check above runs inside the context builders, against the configuration THEY read. `executeTutorLabSupport` (`src/server/tutor-lab-execution/index.ts`) then reads agent configuration a second, later time (needed regardless, to resolve `modelProfileRef`) — but previously never re-checked capabilities against that later read, so an admin narrowing a capability strictly between the two reads (leaving the role enabled and its profile ref unchanged) could let a provider call proceed on context the current configuration no longer authorizes. `executeTutorLabSupport` now re-validates the final configuration itself, using the same `isCapabilityAuthorized` catalogue (never a second allowlist): `get_lesson_context`/`get_lesson_objectives` must still be authorized for both roles, and `get_learning_resources` must still be authorized for Tutor **only when the already-built context actually contains resources** (an optional capability that contributed no content is never required). Any failure here aborts before AUTHORIZE and before any provider call, mapping to the same safe `POLICY_BLOCKED`/`UNAVAILABLE` outcome as a disabled configuration. Four regression tests cover this directly (Tutor loses a required capability; Lab loses a required capability; Tutor's context included resources and loses `get_learning_resources`; Tutor's context had no resources and also lacks `get_learning_resources`, which does not block execution) — see Tests below.

**Correction pass (Blocker 3, role→profile binding):** a resolvable `modelProfileRef` alone is never sufficient authorization. **PR16A update:** the independently-owned `TUTOR_LAB_ROLE_PROFILE_REF` map this section originally described has been removed. Role→profile binding for every provider-backed role (Professor, Tutor, Lab Instructor, Examiner) is now decided by the single shared, DOMAIN-owned `ROLE_RUNTIME_PROFILE_POLICY` (`src/domain/academic-runtime-profile.ts`), consulted through `resolveRoleBoundRuntimeProfile` (`src/server/academic-runtime/profile-registry.ts`). `executeTutorLabSupport` now calls `resolveRoleBoundRuntimeProfile(release.role, config.modelProfileRef)` directly — the same mechanism Professor's own runtime (`src/server/academic-runtime/index.ts`) now uses too, so there is exactly one editable role→profile authority rather than two independently drifting copies. Observable behavior is unchanged: a stored config naming any other resolvable ref — the other Tutor/Lab role's, or `PROFESSOR_COMMERCIAL_V1`, or `EXAMINER_COMMERCIAL_V1` — still fails closed to `UNKNOWN_MODEL_PROFILE` with zero provider calls, even though the shared registry itself would happily resolve any of them.

## Tutor context contents

Exact lesson title/position (`getStudentLessonContext`), a bounded first-page sample of the lesson's own objectives (`getStudentLessonObjectives`) for general orientation, the exact requested objective when the handoff carries one, and permitted learning resources only when the role's own catalogue authorizes them. Never other students' data, unrelated course content, raw package JSON, assessment answers/marking guidance, unrestricted learner history, credentials or admin-only metadata.

**Correction pass (Blocker 4, objective pagination):** `getStudentLessonObjectives` is paginated at 50 objectives per page, but a lesson may declare up to 250 (`src/domain/course-package.ts`). The _requested_ objective (`OBJECTIVE_REINFORCEMENT`'s `release.objectiveId`) is now resolved by paging through up to `ceil(250/50) = 5` pages — a hard, non-unbounded cap — until found; if it is not found anywhere in the lesson, context construction fails `CONTEXT_CONFLICT` rather than silently sending `requestedObjective: null` to the provider. The bounded first-page "objectives" overview field is unaffected and deliberately still capped (never all 250 merely because they exist).

## Lab context contents

Exact lesson title/position, the exact institutional practical (kind/title/instructions) resolved via `get_owned_practical`, and every one of the lesson objectives the practical's own `course_practical_objectives` mapping references. No raw package JSON, no learning resources (catalogue does not permit them for this role), no assessment content.

**Correction pass (Blocker 4, objective pagination):** a practical's mapped objective IDs may be scattered anywhere across up to 250 lesson positions, not only the first 50. Lab context now pages through the same bounded 5-page cap collecting every mapped ID; if the resulting resolved set's size does not exactly equal the practical's own `objectiveIds.length`, context construction fails `CONTEXT_CONFLICT` rather than sending a partial objective set to the provider.

## Audit privacy

Content-minimised throughout: `tutor_lab_content_releases`/`tutor_lab_provider_executions` audit rows carry only identifiers/state/timestamps/budget/usage counters (`role, execution_id, handoff_id, enrolment_id, lesson_id, objective_id, practical_id, state, policy_version, provider call count`) — there is structurally no column for a learner message, provider response, practical instruction body or lesson note body anywhere in migration 028's schema. Verified directly: opening a release and completing an interaction produces no audit content matching the fixture's own instruction-text sentinels.

## Institutional side-effect prohibition

Verified directly: opening a release and reserving an interaction produce zero rows in `attendance_records`, `learning_evidence`, `objective_mastery` or `lesson_progress` for the learner's enrolment. Tutor/Lab responses are learner-support content only; nothing in this checkpoint marks a practical complete, submits an assignment, answers a controlled-assessment question, or mutates any institutional record.

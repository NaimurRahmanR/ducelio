# Live Professor provider-backed execution — Commercial V1 checkpoint

This checkpoint makes the standalone B2 runtime harness (`docs/18-course-agent-engineering.md`) real and testable end to end: a production-capable PROFESSOR provider-backed execution path, composed into the existing `executeRoleCapability` boundary, governed by a new, separately identifiable database surface. Migration 022's historical `PROFESSOR_EXECUTION_V1`/`CONTROL_PLANE_ONLY` path (Checkpoint 1D-B1, `docs/15-academic-execution-governance.md`) is **unmodified** — migration 022 itself is not edited at all — and keeps its exact historical meaning: zero provider budget, control-plane only. This checkpoint's governance is a distinct policy version and table, `PROFESSOR_EXECUTION_V2`/`PROVIDER_BACKED_V1`, introduced entirely in one new migration, `202609130025_commercial_v1_live_professor_execution.sql`.

## Why a separate V2 surface, not a V1 upgrade

Migration 022's `academic_executions` table hard-codes its zero-budget envelope directly into CHECK constraints (`max_provider_calls integer not null default 0 check(max_provider_calls=0)`, and so on) and its own state/reason vocabulary assumes `CONTROL_PLANE_COMPLETE` is the only success reason. Redefining those meanings in place would silently change what a historical V1 row means, and would require editing migration 022 — explicitly excluded from this checkpoint. A new table (`public.academic_provider_executions`) with its own policy/kind literals, its own nonzero-bounded budget columns and its own durable usage ledger keeps V1's historical rows, semantics and tests completely untouched while giving V2 room to express what V1 structurally cannot (a real admitted budget, real usage, more terminal outcomes). `academic_execution_private.controller_keys` (the HMAC trust root) is reused as-is — the trust root is the key store, not a protocol-version-specific secret — but the canonical message carries a distinct protocol tag (`DUCELIO_EXECUTION_HMAC_SHA256_V2`) and policy version (`PROFESSOR_EXECUTION_V2`), so a V1 attestation is structurally unable to authorize a V2 transition and vice versa.

## Required execution order

`src/server/academic-runtime/index.ts`'s `executeRoleCapabilityCore` — the existing, single composition boundary (no second Professor authorization architecture was created) — now performs, in this exact order, once role/delivery/capability/profile checks already pass:

1. Propose a budget (`src/domain/academic-provider-execution.ts`'s `providerExecutionBudgetProposalSchema`) equal to the smaller of the resolved runtime profile's own `budgetPolicy` and the DB-owned hard ceiling (`PROVIDER_EXECUTION_DB_CEILING`) — never larger than either.
2. Call the existing `withValidatedProfessorContent` gateway, which begins its own 30-second academic-content release (migration 021) and retrieves bounded, validated capability output.
3. **Inside that release's own consumer callback**, while it is still `ACTIVE`: AUTHORIZE the V2 execution with that same capped proposal (DB-owned admission — rate limits, activity firewall, and the budget-ceiling check below), then START it (`AUTHORIZED` → `RUNNING`), then run the provider via the existing `runGovernedProviderExecution` harness. Crucially, the harness is invoked with an **effective runtime policy**, not the profile's own raw `budgetPolicy`: `maxProviderCalls`, `maxOutputTokens` and `maxEstimatedCostMicrousd` are replaced with the exact admitted proposal from step 1 (`maxAttempts`, `maxInputContextBytes` and `totalDeadlineMs` are kept from the reviewed profile unchanged, since the DB does not re-negotiate those). A generous profile can therefore never cause the provider itself to be asked for more output tokens, calls or cost headroom than the execution row actually admitted — the DB-authorized ceiling and the runtime's own enforced ceiling are always the same numbers. The call captures the resulting `RuntimeResult`.
4. Return from the callback — **no FINALIZE call is made in here**. The V2 execution is left `RUNNING`.
5. Only once `withValidatedProfessorContent` itself returns — meaning the gateway has already performed its own final principal/activity recheck and closed the release (`COMPLETED`/`ABORTED`/`EXPIRED`) — and only if that recheck/closure succeeded, call FINALIZE: map the captured `RuntimeResult` onto migration 025's bounded terminal vocabulary (`mapRuntimeResultToFinalizeCommand`) and durably reconcile the actual usage in the same trusted transaction that terminalizes the execution.
6. A successful (`SUCCEEDED`) provider response is returned to the caller **only if** FINALIZE itself is confirmed by the database, with a terminal state matching exactly what was requested.

This is why migration 025's FINALIZE operation deliberately does **not** require the bound release to still be `ACTIVE` (unlike AUTHORIZE and START, which do): by design, FINALIZE always runs after that release has already closed.

## Critical success rule

**No `SUCCEEDED` response ever escapes before the release has passed its final recheck and closed successfully.** Concretely:

- If `withValidatedProfessorContent` reports `releaseFinalizationFailed`, or its own final result is not `ok`, the composition boundary discards the captured `RuntimeResult`'s _response_ outright (returns `ABSTAINED`), and best-effort attempts a cleanup FINALIZE (`FAILED`, a reason matching the actual cause) so the V2 row does not dangle `RUNNING` indefinitely — swallowing any failure of that cleanup call itself, since the DB-owned timeout policy remains the real backstop. The RETURNED `RuntimeResult` still carries the real `usage` the provider actually consumed (never the zero placeholder): a discarded response must not make real `providerCalls`/tokens/cost disappear from what the caller observes, even though no answer escapes.
- If the release closed successfully and the real FINALIZE call is attempted but cannot be durably confirmed (transport failure, schema mismatch, a denied/mismatched terminal state), the composition boundary again discards the response and returns `ABSTAINED` — even though the provider itself may have genuinely succeeded and even though a real provider call already happened and consumed real usage. That real usage is still returned to the caller in the `RuntimeResult`, but it is **not** guaranteed to be durably persisted in this specific case: FINALIZE is exactly the operation that could not be confirmed, so whether the database actually recorded it is unknown from here. A `RUNNING` row a client can no longer durably terminalize will still resolve later under the DB's own lazy-expiry sweep (mirroring migration 022's `EXECUTION_TIMEOUT` pattern exactly, now also a valid `FAILED` reason for a genuine controller-observed runtime deadline — see "Runtime outcome mapping" below); no terminal success is ever fabricated to avoid that wait, and the durable ledger is never falsified to make an uncertain outcome look resolved.
- AUTHORIZE and START denials never reach the provider at all: they are caught inside the callback, before `runGovernedProviderExecution` is ever invoked, and mapped to a bounded `ABSTAINED` outcome. A profile whose own `budgetPolicy` already requests fewer than 1 provider call, output token or cost unit short-circuits to `BUDGET_BLOCKED`/`PRE_CALL` without even attempting AUTHORIZE, since migration 025 structurally requires an admitted nonzero budget.

To state this precisely, since "usage is durable" is not a single guarantee:

- **When FINALIZE succeeds**, the actual bounded usage `RuntimeResult` reported is persisted atomically with the execution's own terminalization (same transaction, same trusted call) — this is the only case where durability is guaranteed.
- **When the release/gateway discards the response but FINALIZE's own cleanup call still succeeds**, usage is likewise durably recorded, tied immutably to the (non-`SUCCEEDED`) terminal state.
- **When FINALIZE itself cannot be durably confirmed**, no success escapes and the returned `RuntimeResult` still truthfully carries the locally observed usage — but that specific usage may or may not have reached the database. The execution row itself will still resolve later, either because a delayed FINALIZE attempt eventually succeeds or because the DB's own lazy-expiry sweep marks it `TIMEOUT`/`EXECUTION_TIMEOUT` once its window elapses; this checkpoint does not claim the in-memory number and the durable ledger are reconciled in that specific window.

## DB-owned V2 budget ceiling

Independent of whatever a runtime profile, course package or stored agent configuration proposes, `public.academic_provider_executions`' own CHECK constraints cap every admitted execution at:

| Field                         | Hard ceiling                  |
| ----------------------------- | ----------------------------- |
| `max_provider_calls`          | 1..3                          |
| `max_output_tokens`           | 1..4000                       |
| `max_estimated_cost_microusd` | 1..200000 (up to 20 US cents) |

These are also the exact bounds `academic_execution_private.verify_command_v2` requires of a signed proposal before it will even verify a MAC — a proposal above the ceiling is rejected at the cryptographic layer (`UNTRUSTED_EXECUTION`), a stronger guarantee than a runtime check reached after verification; a proposal of exactly `0` for any field is verifiable but is refused by AUTHORIZE's own business logic (`BLOCKED`/`OUT_OF_ENVELOPE`). `src/domain/academic-provider-execution.ts`'s `PROVIDER_EXECUTION_DB_CEILING` constant must stay byte-for-byte in step with these three numbers. This ceiling governs both sides of the boundary identically: the proposal AUTHORIZE admits, and — since the composition boundary constructs its effective runtime policy from that same admitted proposal (see "Required execution order" above) — the provider request `runGovernedProviderExecution` actually sends. A runtime profile's own, possibly larger, `maxProviderCalls`/`maxOutputTokens`/`maxEstimatedCostMicrousd` therefore never reaches the provider; only `maxAttempts`, `maxInputContextBytes` and `totalDeadlineMs` come from the profile unmodified. Matching the existing documented distinction in `src/domain/academic-runtime.ts`: provider call count and the requested output-token ceiling are meaningfully pre-call quantities; input-token count and monetary cost can only ever be known from what a provider actually reports, so their enforcement at FINALIZE is post-call reconciliation, never a pre-call spending guarantee — a `SUCCEEDED` claim whose own reported output tokens or cost already exceeds its execution's admitted ceiling is rejected as self-contradictory (`INVALID_INPUT`), and a reported `provider_calls` count above the admitted ceiling is rejected regardless of outcome.

## Durable, content-free usage ledger

`public.academic_provider_execution_usage` closes the previously-documented gap: exactly one row per execution (`execution_id` is its primary key), written only by FINALIZE in the same transaction that terminalizes the execution, and made permanently immutable by its own `BEFORE UPDATE OR DELETE` guard (stricter than the execution table's own "terminal rows are immutable" rule — this table has no non-terminal state to begin with). It persists `provider_calls`, `attempts`, `input_tokens`, `output_tokens`, `estimated_cost_microusd` and `elapsed_ms` only — there is structurally no column for prompt text, response text, resource bodies, assessment prompts/answers, arbitrary provider payloads, credentials or secrets. Usage is recorded truthfully regardless of whether the response itself may escape: a `BUDGET_BLOCKED`/`POST_CALL` outcome, a provider `FAILED`, a `TIMEOUT` or a `CANCELLED` all still persist their real reported numbers. Only `govern_professor_provider_execution` (SECURITY DEFINER, reachable only through a verified MAC plus the authenticated learner session) can ever write to either table; both are revoked from `public`, `anon`, `authenticated` and `service_role` directly, with the same effective-ACL assertion pattern as migrations 022 and 024 closing this migration's own deployment.

## Runtime outcome mapping

`mapRuntimeResultToFinalizeCommand` (`src/domain/academic-provider-execution.ts`) is a pure function mapping every `RuntimeResult` outcome (`src/domain/academic-runtime.ts`) onto migration 025's bounded FINALIZE vocabulary:

| RuntimeResult outcome | FINALIZE state   | reason                                                                                                                                                                         |
| --------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `SUCCEEDED`           | `SUCCEEDED`      | `PROVIDER_COMPLETE`                                                                                                                                                            |
| `FAILED`              | `FAILED`         | the reported `ProviderFailureCode`                                                                                                                                             |
| `ABSTAINED`           | `ABSTAINED`      | the reported `RuntimeAbstentionReason`                                                                                                                                         |
| `ESCALATED`           | `ESCALATED`      | `HUMAN_REVIEW_REQUIRED`                                                                                                                                                        |
| `BUDGET_BLOCKED`      | `BUDGET_BLOCKED` | fixed `BUDGET_BLOCKED`, with `budgetStage` carrying `PRE_CALL`/`POST_CALL`                                                                                                     |
| `TIMEOUT`             | `FAILED`         | `EXECUTION_TIMEOUT` (an equally honest outcome; migration 025 reserves its own `TIMEOUT` state for the DB's own lazy-expiry sweep, mirroring migration 022's existing pattern) |
| `CANCELLED`           | `CANCELLED`      | `CANCELLED`                                                                                                                                                                    |

`EXECUTION_TIMEOUT` is a valid `FAILED` reason consistently across every layer that checks it: the table's own lifecycle `CHECK` constraint, `govern_professor_provider_execution`'s FINALIZE reason whitelist, `verify_command_v2`'s signable-reason set, and `providerExecutionSnapshotSchema`'s `FAILED` reason list on the TypeScript side. A genuine controller-observed deadline (`RuntimeResult` outcome `TIMEOUT`) is reported through the same, ordinary FINALIZE-from-`RUNNING` path as any other governance/provider failure reason — never a special case a database rejection could turn back into a dangling `RUNNING` row.

`mapRuntimeResultToFinalizeCommand` validates the real `RuntimeUsage` strictly against the durable ledger's own bounded schema (`providerExecutionUsageReportSchema`) rather than silently clamping an out-of-range value into something FINALIZE would accept: a legitimate `RuntimeUsage` should already fit, now that the runtime harness itself is capped by the same effective policy AUTHORIZE admitted. If an internally impossible value ever appeared regardless, the mapping throws (`ImpossibleUsageError`) and the composition boundary treats that exactly like any other FINALIZE-confirmation failure — fail closed, never send a falsified number to the durable ledger and never fabricate a terminal success.

Admission-time refusals that never reach `runGovernedProviderExecution` at all (an out-of-envelope or rate-limited AUTHORIZE) never produce a fake execution record purely to inflate metrics: AUTHORIZE's own structured `BLOCKED` admission is itself the complete, truthful, durably-audited record of that refusal.

## What this checkpoint does not do

No provider secret, endpoint or vendor SDK is added; the code-owned production runtime/model-profile registry (`src/server/academic-runtime/profile-registry.ts`) remains deliberately empty, so in production every stored `modelProfileRef` still fails closed to `ABSTAINED`/`UNKNOWN_MODEL_PROFILE` before any of this governance is even reached — this checkpoint makes the _path_ real and independently testable with deterministic fake adapters, not hosted provider acceptance. No UI, route or Server Action calls `executeRoleCapability`. TUTOR/LAB_INSTRUCTOR/EXAMINER/COUNSELLOR remain `NO_EXECUTION_PATH` regardless of stored configuration, unchanged from the prior checkpoint. Migrations 001–024 are byte-for-byte unchanged.

Read-only preflight/introspection (`HOSTED_DATABASE`, `MIGRATIONS`, `RLS_ACL`) never calls either gate and remains available with `ACCEPTANCE_DATABASE_URL` alone.

**TLS (independent-review finding 4):** the direct database connection no longer unconditionally disables certificate verification. ## 2. True PostgreSQL concurrency

**Current evidence:** hosted acceptance run `1790606638430-8qftcb` of `npm run acceptance:concurrency` executed all six scenarios with no FAIL, BLOCKED or NOT_RUN result: `INITIAL_VS_INITIAL`, `RECOVERY_VS_RECOVERY`, `NEVER_TWO_REVISION_ONES`, `LATE_INITIAL_FINALIZE_VS_RECOVERY_AUTHORIZE`, `REGRADE_VS_COMPLETION` and `COMPLETION_VS_COMPLETION`. Current scoped result: **HOSTED-TESTED — 6 PASS / 0 FAIL / 0 BLOCKED / 0 NOT_RUN**. For `REGRADE_VS_COMPLETION` the observed serial order was `COMPLETION_FIRST`. The two application races prove that both operations were released together from one client-side start gate and that the resulting database state was valid; they do not prove simultaneous server-transaction overlap.

**Prerequisite:** a real PostgreSQL environment permitting multiple simultaneous connections — prefer the dedicated hosted acceptance database over production.

**Required race tests** (independent connections/processes):

- **Examiner initial grading:** two simultaneous initial AUTHORIZE attempts for the same target → exactly one durable initial claim, no duplicate provider authority, no duplicate result.
- **Initial grading vs recovery:** race a late initial execution/finalization against institutional recovery admission → never two revision-1 results; one side deterministically loses according to database authority.
- **Recovery vs recovery:** two simultaneous recovery admissions for the same source → exactly one recovery execution, one bounded replay/denial, no duplicate provider-call authority. This directly exercises `examiner_recovery_one_per_source` under real concurrent contention, not just PGlite's sequential unique-index proof.
- **Grading finalization vs completion:** completion never sees an impossible partially-finalized result; either grading commits first and completion evaluates it, or completion refuses because authoritative grading remains incomplete.
- **Regrade vs completion:** where the current authority permits the operation, current result revision and completion remain transactionally consistent; completion cannot silently use a superseded revision.
- **Duplicate course completion:** two simultaneous completion attempts on the same enrolment → one durable completion result/receipt, deterministic idempotent replay, no duplicate institutional completion record. This directly exercises `attemptCommercialV1CourseCompletion`'s replay guarantee under real concurrent contention, not just PGlite's sequential proof from Checkpoint C's own tests.

The harness therefore establishes **HOSTED-TESTED** evidence for all six named scenarios in the dedicated acceptance environment. This is not PRODUCTION-PROVEN, and the application races' client-side simultaneous release is not evidence that the server transactions overlapped in time.

**How the two application races are implemented (`scripts/acceptance/concurrency-app-races.mjs`, hosted-executed by the run above):** unlike `NEVER_TWO_REVISION_ONES` (two raw privileged transactions racing a unique index), both drive the real Ducelio app server through the same fail-closed acceptance route, loopback deterministic provider stub and genuine hosted sessions as section 4a, so every grading/recovery/regrade transition is attested only by the unmodified production authority modules:

- `LATE_INITIAL_FINALIZE_VS_RECOVERY_AUTHORIZE` — a learner's real initial grading request passes AUTHORIZE/START/CONTEXT_READ and is held in flight while the genuine 20-second DB lease expires (never shortened or edited); a real replay of the same path lets migration 031's lazy-timeout authority mark that execution `TIMEOUT`; the still-alive original invocation's late FINALIZE and an admin's real `recoverExaminerTarget` are then released from one client-side start gate. PASS requires the original to stay `TIMEOUT` with no result or usage, exactly one successful admin-owned recovery claim, exactly one valid revision 1 owned by that recovery, exactly two provider calls, and idempotent replays. Because the `EXAMINER_COMMERCIAL_V1` provider deadline (15 s) is shorter than the lease (20 s), a provider-only hold could never outlive the lease; the original request is therefore held on delivery of its already-served context-read response inside the acceptance-only preload (acceptance tooling only; no production source changed).
- `REGRADE_VS_COMPLETION` — on a dedicated completion-ready enrolment whose QUIZ_1 result comes from real answered responses and the real grading FINALIZE (other components are seeded), an admin's real regrade is held at its provider call after AUTHORIZE/START/CONTEXT_READ; its FINALIZE and the learner's real `attempt_commercial_v1_course_completion` are then released from one start gate. PASS accepts exactly two serial orders: regrade first (one valid next revision; the one receipt's score equals the post-regrade course score) or completion first (one receipt from the then-current result; the regrade refused `TARGET_NOT_ELIGIBLE` with no next revision). Anything else — a receipt from a superseded result, a post-completion regrade revision, two receipts/audits, an invalid or partial revision, duplicate regrade execution/provider history — is FAIL.

Both additionally need the section 4a prerequisites (`ACADEMIC_EXECUTION_*` with the matching hosted key installed); without them they report BLOCKED. Both also reuse the one synthetic acceptance learner, so they need real capacity in that learner's production fresh-admission windows (5 claims per 60 s, 30 per hour, per execution family) — initial and recovery claims for the late-initial race, initial and regrade claims for regrade-vs-completion. Before any fresh grading, and again immediately before the recovery/regrade admission, the harness reads each family's counts against the hosted database clock (read-only; history is never reset, deleted, backdated or bypassed). If recent synthetic acceptance activity has exhausted a window, that race is **BLOCKED**, naming the family and its count/window — not FAIL — until the real window has capacity again; it does not wait up to an hour. This is separate from waiting for genuinely live leases. As elsewhere, simultaneous client-side dispatch proves both operations were released together, not that the server transactions overlapped in time.

## 4a. Real-application examiner acceptance (`npm run acceptance:examiner-app`)

`scripts/acceptance/examiner-app.mjs` starts the real Ducelio app locally (`next dev`, loopback only) against the hosted acceptance project and drives the existing production entrypoints over HTTP through the acceptance-only route `src/app/api/acceptance/examiner-app/route.ts`: learner `submitControlledAssessmentAndGrade` → `gradeControlledAssessmentAttempt`, admin `recoverExaminerTarget`, admin `regradeControlledAssessment`. Passing that preload through `NODE_OPTIONS` is **not** treated as sufficient: the installed wrapper is marked with a second per-run secret (`ACCEPTANCE_PROVIDER_REDIRECT_TOKEN`), and the route gate itself — per request, inside the exact process serving it, before the body is read or anyone is signed in — calls the CURRENT `globalThis.fetch` with an in-process sentinel request that only that marked wrapper answers with its marker. ## 5. Live AI provider acceptance (`npm run acceptance:live-provider`)

**Correction (live-provider acceptance checkpoint):** an earlier version of this section named `ACADEMIC_PROVIDER_BASE_URL`/`ACADEMIC_PROVIDER_API_KEY` as the Commercial V1 provider configuration. That has been stale since PR22's native AI routing (`docs/32-commercial-v1-native-ai-routing.md`).

**Current configuration.** Commercial V1 production profiles route natively. The only provider credentials are the server-only `OPENAI_API_KEY` (every `OPENAI_RESPONSES` profile, including `EXAMINER_COMMERCIAL_V1`) and `ANTHROPIC_API_KEY` (every `ANTHROPIC_MESSAGES` profile: `LAB_INSTRUCTOR_COMMERCIAL_V1` and, since the Operations Engineer routing correction, the internal `OPERATIONS_ENGINEER_PLATFORM_V1` / `claude-opus-5-5` profile, which the live-provider harness below exercises only as the `LIVE_PROVIDER:ANTHROPIC_OPERATIONS_ENGINEER` smoke). Endpoints, model ids, tariffs and budget policies stay code-owned in `src/server/academic-runtime/provider.ts` and `src/server/academic-runtime/profile-registry.ts`; no environment variable, browser, course package or stored agent configuration can choose them. Without the relevant key, `resolveAdapterForProfile` returns `null` and execution fails closed to `NO_PROVIDER_CONFIGURED` before any network call.

`ACADEMIC_PROVIDER_BASE_URL`/`ACADEMIC_PROVIDER_API_KEY` configure only the **legacy** generic `HTTP_JSON` adapter (`resolveConfiguredProvider`), kept for backward compatibility. No current Commercial V1 production profile routes through it, so it is not required for Commercial V1 and is not a live-provider acceptance target.

**Explicit double authorization.** A key existing — in `.env.local` or the shell — is never permission to spend. `npm run acceptance:live-provider` makes a provider request only when BOTH `ACCEPTANCE_LIVE_PROVIDER_OPT_IN` is exactly `true` AND the operator passes `--authorize-live-provider` (`npm run acceptance:live-provider -- --authorize-live-provider`). Without both, every surface reports `BLOCKED` (`EXPLICIT_AUTHORIZATION_REQUIRED`), no server starts and zero provider requests are made. `npm run acceptance:hosted` never makes a paid request: its `LIVE_PROVIDER` row is always `BLOCKED` and points at the dedicated command.

**Explicit single-surface selection.** An authorized run must also name exactly one surface on the command line with a fixed selector; there is no run-all mode. The selector is read from the command line only, never from the environment:

```
npm run acceptance:live-provider -- --authorize-live-provider --surface=OPENAI_EXAMINER
npm run acceptance:live-provider -- --authorize-live-provider --surface=ANTHROPIC_LAB
npm run acceptance:live-provider -- --authorize-live-provider --surface=ANTHROPIC_OPERATIONS_ENGINEER
```

A missing selector (`SURFACE_SELECTION_REQUIRED`), an unrecognized selector value (`UNKNOWN_SURFACE_SELECTOR`, never echoed) or more than one selector (`MULTIPLE_SURFACE_SELECTORS`) BLOCKS every surface before any server starts. Only the selected surface may run; every other surface reports `NOT_RUN` (`NOT_SELECTED`) with zero calls. If the selected surface's key is absent it BLOCKS on its own. Because both Anthropic surfaces share `ANTHROPIC_API_KEY`, this selection is what keeps one configured Anthropic key from causing both a Sonnet and an Opus request.

**Surfaces (exactly three).**

| Surface                                       | Production profile                | Adapter / model                          | Role / capability                                       |
| --------------------------------------------- | --------------------------------- | ---------------------------------------- | ------------------------------------------------------- |
| `LIVE_PROVIDER:OPENAI_EXAMINER`               | `EXAMINER_COMMERCIAL_V1`          | `OPENAI_RESPONSES` / `gpt-5.6-luna`      | `EXAMINER` / `grade_controlled_assessment`              |
| `LIVE_PROVIDER:ANTHROPIC_LAB`                 | `LAB_INSTRUCTOR_COMMERCIAL_V1`    | `ANTHROPIC_MESSAGES` / `claude-sonnet-5` | `LAB_INSTRUCTOR` / `tutor_lab_support`                  |
| `LIVE_PROVIDER:ANTHROPIC_OPERATIONS_ENGINEER` | `OPERATIONS_ENGINEER_PLATFORM_V1` | `ANTHROPIC_MESSAGES` / `claude-opus-5-5` | `OPERATIONS_ENGINEER` (platform) / `read_system_health` |
